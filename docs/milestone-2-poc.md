# Milestone 2 — Compression Proof of Concept

Date: 2026-11-01 · Version 0.2.0 · Status: **complete in the dev
environment; on-device iPhone test pending**

## What was built

A working, installable PWA that:
1. imports a PDF through the iOS Files picker;
2. analyzes it;
3. compresses it locally in a Web Worker;
4. verifies the result;
5. reports the actual size reduction;
6. exports it via the Share Sheet / Save to Files, or as a download.

The engine is the Milestone 1 design: MuPDF/WASM, rewriting image XObject
streams in place. Pages are never rasterized.

| Requirement | Status | Evidence |
|---|---|---|
| Import a scanned PDF | ✅ | e2e: file input → analysis |
| Inspect it | ✅ | analysis screen; unit tests for pages, geometry, rotation, images, DPI, JPEG quality, text, links, outline, annotations |
| Compress locally | ✅ | worker; e2e shows **0 network requests** during processing (page and worker) |
| Export | ✅ | e2e downloads the output and checks it is a `%PDF-` file of the reported size |
| Report actual reduction | ✅ | sizes come from the generated bytes; nothing is estimated |
| Confirm the output opens | ✅ | output is reopened and every page rendered (decodes every image); also opened by **pdf.js** in tests |
| Several settings tested | ✅ | 5 fixtures × 4 profiles in the test suite; benchmark below |

Reading the table:
- **Lossless ≈ 0%** on these fixtures because they are already tightly
  packed. Real-world PDFs with duplicate or unused objects will gain more.
- The **q75 source** is skipped by High/Balanced because re-encoding an
  already-lower-quality JPEG adds generation loss for no gain. Compact
  shrinks it by downsampling 300→200 DPI.
- **Compact** downsamples 300 DPI scans to 200 DPI. Text stays legible, but
  this is the profile to check visually. Milestone 3 adds a proper
  SSIM/preview comparison.
- **Time is dominated by JPEG encoding and the verification render.**
  Expect iPhone times to be 2–4× these until measured.

## Engineering decisions made in this milestone

- **Area-average downsampling**, not bicubic. It avoids ringing halos around
  text. It works on views of WASM memory, with no extra copies.
- **Exact DPI measurement:** MuPDF returns the same cached image object for
  the same PDF object, so each draw call maps to its object exactly. DPI is
  the minimum over all placements, so a reused image is never undersampled.
- **JPEG generation-loss guard:** source quality is estimated from the
  quantization tables. An image is skipped when it is already at or below
  the target quality (and not being downsampled).
- **Replace only if ≥5% smaller**, so an image is never made bigger.
- **Conservative skips** (reported to the user, never silent): 1-bit,
  masks, SMask/Decode images, CMYK/Indexed/Lab/Separation, tiny images.
- **PDF/A-1 detection** disables object streams, which that standard
  forbids.
- **Cancellation = worker termination.** It is the only reliable way to stop
  synchronous WASM work, and it frees all WASM memory.
- **Own service worker** (about 60 lines) instead of vite-plugin-pwa / Workbox.
  That is one less dependency, the npm audit is clean, and it is precache-only
  with no runtime caching.

Two bugs were found and fixed through testing:
- **SW first-install reload:** the page reloaded itself when the service
  worker first took control, which could interrupt first use. It now
  reloads only when you accept an update.
- **`Vary` header cache misses:** CSS/JS requests carrying an `Origin`
  header missed the cache offline. Fixed with `ignoreVary`.

## Addendum (0.2.1): first on-device test and encoder change

Real-world test by the owner on iPhone: a 102.8 MB, 33-page image-only scan.
- Analysis, compression, verification (all checks green), offline use and
  memory all worked on the device. Processing took about 1 minute, and the
  103 MB file stayed within iOS memory limits.
- **Balanced: 0%.** All 33 images were "kept: would not save ≥5%".
  **Compact: −18.8%.**
- **Save to Files produced a .txt** with the file's name.

Root causes and fixes:
1. `navigator.share({ files, title })`: iOS shares `title` as a separate
   text item. Now `{ files }` only.
2. MuPDF's `Pixmap.asJPEG` always writes progressive 4:4:4 (verified from
   the SOF marker). Phone and scanner JPEGs are 4:2:0. Re-encoding a 4:2:0
   source as 4:4:4 spends about a third more bytes on chroma the source no
   longer has.

Encoder comparison on a 300 DPI page saved as q95 4:2:0, re-encoded:

| Encoder | Size | Saved | SSIM @300 DPI | SSIM @150 DPI |
|---|---|---|---|---|
| source | 2.455 MB | — | — | — |
| MuPDF q90 4:4:4 | 1.793 MB | 27.0% | 0.979 | 0.994 |
| mozjpeg q90 4:2:0 | 1.266 MB | **48.5%** | 0.975 | 0.994 |
| mozjpeg q85 4:2:0 | 0.898 MB | 63.4% | 0.970 | 0.991 |

For a source that is already q90 4:2:0, re-encoding at q90 saves under 10%
with any encoder. Further savings need lower quality or lower resolution.
That is a property of the source, not of the tool. A visual check of 4:2:0
on red stamp edges and dark text at 1.5× showed no visible difference.

### Second finding: photo-sized pages

The owner's analysis screen showed 33 DCT colour images, 3024–5712 ×
4032–5712 px, JPEG quality ≈93, on pages of 59.5 × 79.3 in (and 42 × 56 in).
These are iPhone camera photos converted to PDF with the page sized at 72 DPI.
DPI-based downsampling therefore saw 72 DPI and never triggered. Pages whose
long side exceeds 17 in are now evaluated as if printed at Letter size: a 4032
px long side is 367 DPI, a 5712 px long side is 519 DPI.

| iPhone photo → PDF fixture (q93 4:2:0, 72 DPI page) | Balanced | Compact |
|---|---|---|
| 12 MP | −17.3% (q93 → q90, no downsampling) | −90.5% (→ 200 DPI at Letter) |
| 24 MP | −84.8% (→ 300 DPI at Letter) | −96.7% |

### Third finding: heap fragmentation across jobs

In one WASM instance the MuPDF heap grew 79 → 220 MB over six jobs on 12 MP
photos, in steps of one decoded image (36.6 MB). WASM memory cannot shrink,
so the client now recycles the worker after every compression job.
`test/memprobe.test.ts` reproduces the measurement.
